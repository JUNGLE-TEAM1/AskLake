# Job 상태와 실행 결과 정책

## 목적

수집/처리 목록에서 **작업의 현재 운영 상태**와 **가장 최근 실행의 결과**를 분리한다. 이 기준이 없으면 `실패`, `취소`, `일시정지`가 모두 작업 상태처럼 보이고, 배치 작업과 실시간 작업의 버튼 의미도 모호해진다.

이 문서는 `/jobs` 목록, `/jobs/:jobId`, `/jobs/:jobId/runs`, Job command API가 공유하는 기준이다.

## 용어

| 구분 | 의미 | 목록 표시 위치 |
| --- | --- | --- |
| 작업 상태 | 지금 이 Job이 새 실행을 받을 수 있는지, 실행 중인지, 의도적으로 멈췄는지 | `상태` 열, 현황 카드, 상태 필터 |
| 실행 결과 | 가장 최근 Run이 성공, 실패, 취소 중 무엇으로 끝났는지 | `마지막 실행` 열의 시각과 결과 아이콘, 실행 이력 |
| 실행 주기 | 수동, 배치, 실시간처럼 Job을 시작하는 방식 | `실행 주기` 열 |

## 작업 상태

목록의 작업 상태는 아래 네 가지로 제한한다.

| 상태 | 의미 | 기본 액션 |
| --- | --- | --- |
| `scheduled` / 실행 대기 | 활성 스케줄이 있고 현재 실행은 없다. 수동 작업도 실행을 기다리는 기본 상태로 포함한다. | 배치: 즉시 실행·스케줄 일시중지, 실시간: 실행 |
| `running` / 실행 중 | 현재 Run이 진행 중이다. | 배치: 실행 취소, 실시간: 실행 중지 |
| `paused` / 실행 일시정지 | checkpoint가 준비된 뒤 사용할 확장 상태다. 현재 목록에서는 노출하지 않는다. | checkpoint 기반 실행 재개 |
| `stopped` / 자동 실행 중지 | 반복 예약 또는 실시간 자동 시작을 의도적으로 껐다. 목록 상태 badge는 노란색 `자동 실행 중지`로 통일한다. | 배치: 스케줄 재개, 실시간: 실행 |

`failed`, `canceled`는 새 작업 상태로 만들지 않는다. legacy 응답에 이 값이 들어오면 frontend는 `scheduled`로 정규화하고 최근 Run 결과로 보여 준다.

## 마지막 실행 결과

`마지막 실행` 셀에는 항상 실제 실행 시각과 결과 아이콘을 함께 표시한다. `방금 취소`, `실행 실패` 같은 결과 문구로 시각을 대체하지 않는다.

| 최근 Run 결과 | 아이콘/색 | 목록 행동 |
| --- | --- | --- |
| 성공 | 초록 체크 | 작업 상태는 실행 대기 |
| 실패 | 빨간 경고 | 작업 상태는 실행 대기, `재실행` 제공 |
| 취소 | 회색 X | 작업 상태는 실행 대기, `즉시 실행` 제공 |
| 실행 중 | 스피너 | 작업 상태는 실행 중 |
| 일시정지 | 노란 Pause | checkpoint 지원 이후에만 노출 |

## 작업 현황 표시 원칙

작업 현황 카드는 현재 상태라는 한 축만 보여 준다. `전체 작업`/`실행 중`/`실행 대기`/`자동 실행 중지` 네 개를 사용하며, 전체를 제외한 세 상태 집계는 서로 겹치지 않는다.

`최근 실행 실패`는 작업 상태 분포가 아니라 최신 Run 결과이므로 현황 카드에 섞지 않는다. 별도의 shadcn `Alert`로 보여 주고, `실패 작업 보기`를 누르면 `lastRunOutcome=failed`를 적용한다. 이 결과 필터는 현재 상태 필터와 독립적이므로 `실행 대기 + 최근 실행 실패`처럼 조합할 수 있다. 취소는 별도 현황 항목으로 만들지 않고 실행 이력과 마지막 실행 아이콘으로만 확인한다.

## 목록 액션 계산 원칙

목록 액션은 하나의 상태 문자열로 결정하지 않고 아래 세 축을 독립적으로 계산한다.

| 판단 축 | 결정하는 UI |
| --- | --- |
| 현재 Run이 실행 중인가 | 배치는 `실행 취소`, 실시간은 `실행 중지` |
| 자동 스케줄이 활성화됐는가 | 배치의 `스케줄 일시중지` 여부. 실시간은 이 축을 별도 버튼으로 노출하지 않음 |
| 최근 Run 결과가 무엇인가 | 실패면 `재실행`, 취소·성공·실행 전이면 `즉시 실행` |

따라서 배치 Job의 최근 Run을 실패 또는 취소해도 스케줄 제어 버튼은 사라지지 않는다. `실행 취소`는 현재 Run만 끝내고, `스케줄 일시중지`만 다음 예약을 끈다. 수동 Job처럼 자동 스케줄이 없는 Job에는 스케줄 제어 버튼을 표시하지 않는다.

## 배치와 실시간의 차이

### 현재 릴리스의 배치 Job

- `실행 취소`는 현재 Run만 끝낸다.
- Job은 즉시 `실행 대기`로 돌아가며 다음 예약은 유지한다.
- `실행 일시정지` 버튼은 checkpoint가 준비될 때까지 노출하지 않는다.
- legacy `paused` 상태를 받으면 `실행 대기`로 정규화하고 `다시 실행`만 제공한다.

### 현재 릴리스의 실시간 Job

- 실시간 수집은 활성 상태라면 자동 재시작될 수 있으므로, 사용자가 멈추려는 의도에는 `실행 취소`보다 `실행 중지`가 맞다.
- `실행 중지`는 `stopped`로 바꾸어 자동 재연결과 새 Run 시작을 막는다.
- 실행 중이면 `실행 중지`, 실행 중이 아니면 `실행` 하나만 제공한다. 실시간 Job에는 `즉시 실행`, `스케줄 일시중지/재개`라는 문구를 사용하지 않는다.
- `실행`은 `run` 또는 실패 후 `retry`로 실제 새 Run을 시작한다. 실시간 UI에서는 `resumeSchedule`만 호출해 실행 대기에 머무르는 흐름을 사용하지 않는다.
- 운영자가 일시적인 장애 복구를 원할 때만 내부 정책에 따라 실패 후 `실행 대기`와 backoff 재시작을 적용한다.

## 액션 문구와 아이콘

| 대상 | 중지 액션 | 재개 액션 | 이유 |
| --- | --- | --- | --- |
| 배치 스케줄 | `CalendarOff` + 스케줄 일시중지 | `Calendar` + 스케줄 재개 | 앞으로 예약된 실행을 끄고 켠다는 의미다. |
| 실시간 수집 | `Square` + 실행 중지 | `Play` + 실행 | 현재 지속 수집을 멈추고 다시 시작한다는 의미다. |
| 배치 실행 중 | `X` + 실행 취소 | 이후 즉시 실행 | 현재 Run만 종료하며 다음 예약은 유지한다. |

실행 일시정지는 Spark checkpoint에서 동일 Run을 이어갈 수 있을 때만 `Pause/Play`로 추가한다. 현재는 checkpoint가 없으므로 취소와 구분되는 실제 동작을 보장할 수 없어 UI에 노출하지 않는다.

## 현재 구현과 후속 API 기준

현재 backend의 `pause` 뒤 `run`은 Spark checkpoint를 복원하는 진짜 resume이 아니라 새 Run을 시작한다. Spark를 나중에 붙이는 현재 범위에서는 `pause`를 목록 UI에서 숨기고, checkpoint 도입 후 `pause`와 실제 `resume` endpoint를 함께 구현한다.

정책 적용 PR에서는 다음 API 데이터를 보장한다.

- Job: `status`, `schedule`, `nextRun`
- 최신 Run: `status`, `startedAt`, `endedAt`, `errorSummary`
- 목록 facets: `owners`, 작업 상태 count, `latestRunOutcomeCounts`
- 목록 query: `status`, `owner`, `scheduleKind`, `lastRunOutcome`

## 적용 순서

1. 이 문서를 기준으로 API contract와 mock fixture를 갱신한다.
2. 취소/실패가 Job을 `scheduled`로 되돌리도록 backend와 mock을 맞춘다.
3. `마지막 실행`에 실제 시각과 결과 아이콘을 표시한다.
4. `최근 실행 실패` Alert와 독립 결과 필터를 추가한다.
5. Spark checkpoint 지원 뒤 `실행 일시정지`와 `실행 재개`를 다시 도입한다.
